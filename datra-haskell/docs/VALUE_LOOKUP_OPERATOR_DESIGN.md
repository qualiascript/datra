# Foliage-ordered value lookup

## Summary

Change `~` from name-oriented parser sugar into a first-class prefix operator
over string expressions. The result is always a map of lookup rows. Each row
contains a generated key and a `Maybe` containing the value currently bound to
that key:

```datra
(
  (key : "arg0"; value : Just 123);
  (key : "arg1"; value : nothing);
  ...
)
```

For a concrete string, including a total string template, the result is a
singleton map. For a non-total string template, the result contains every key
generated by the template's capture family. Rows are ordered by the canonical
`FoliageMap` traversal of that family.

For example:

```datra
~"arg%Nat"
```

has one row for `"arg0"`, one for `"arg1"`, and so on. If `arg0` is bound to
`123` and `arg1` is absent, its first two rows have the shape shown above.

A template capture is admissible exactly when it can participate in the
ordinal-indexed map projection used by a `^` generic. A capture such as `Any`,
which has no such map projection, is a compilation error. This operator does
not invent a second definition of enumerable type.

String-template matching is also changed to validate captures with ordinary
function-domain preparation rather than generic `of` membership. Captured text
must be canonical. Thus `"arg%(_x : Nat)"` generates and matches `"arg4"`, not
`"arg(_x := 4)"`.

## Goals

1. Make the right operand of `~` an evaluated string expression.
2. Return a map even for a single concrete key.
3. Include every key described by an admissible string template, whether or
   not that key exists in the current scope.
4. Store lookup success or absence in each row's `value` field as `Just value`
   or `nothing`.
5. Use `FoliageMap` as the sole ordering of rows generated from a non-total
   capture family.
6. Reuse exactly the ordinal-indexed-family rules used to give `^` generic
   functions a map-access view.
7. Reject non-enumerable captures, such as `Any`, while compiling the lookup.
8. Use function-domain preparation for canonical string captures.
9. Preserve a distinct, strict representation for compiler-generated lexical
   references and ordinary identifier evaluation.

## Non-goals

- `~` does not return a function. `~"arg%Nat" 4` is not the lookup interface;
  the map already contains the row for `"arg4"`.
- `~` does not search an arbitrary map. It searches the lexical scope in which
  the operator is evaluated.
- This change does not alter ordinary identifier references or `value.name`
  scope access.
- This change does not alter declarative syntax matching introduced by the
  syntax `%` operator. Syntax holes capture ASTs; they are not canonical string
  captures.
- Foliage traversal determines result order only. It does not change the
  ordinal order of the capture family itself.
- Absence is optional, but errors from evaluating an existing binding are not
  converted to `nothing`.

## Current behavior

`Parsing.valueOfExpression` currently parses one or more names and expands each
name into:

```haskell
ScopeAccess
  (contextualAccess (IdentifierString "_this"))
  (IdentifierReference name)
```

Consequently:

- `~a` treats `a` as the literal name `"a"`;
- `~(a, b)` is a special list of two strict accesses;
- a missing name raises `UnknownIdentifier` or a named-access error;
- only the selected payload is returned; and
- no `~` node survives in the AST.

`DatraLanguage.AST.Source` recognizes the expanded shape and renders it as `~`.
`FunctionClosure` and canonical dependency rendering also rely on that shape
for strict generated references. That coupling must be removed because the new
operator returns a map of optional values and cannot represent a strict closure
dependency.

String templates currently become string federations. Reverse matching splits
the input at literal boundaries and uses the general federation-selection
logic behind `of` for each interpolation. That path can preserve an identifier
assignment spelling where the template needs the canonical spelling of the
prepared capture payload.

## Result semantics

### Lookup row

Every result member is a two-member named map:

```datra
(key : <concrete string>; value : <Maybe resolved value>)
```

The `key` member contains the exact generated query string. The `value` member
is:

- `Just <resolved value>` when the key resolves in the current scope; or
- `nothing` when no binding resolves for the key.

The row is a regular map, not an argument-map permutation. Preserve its
two-member boundary with `makeAtlasMapPreservingSingleton` or an equivalent
constructor. The outer lookup result is also a preserved map, including in the
zero- and one-row cases, so callers can uniformly use map access:

```datra
(~"arg%Nat")[0].key
(~"arg%Nat")[0].value
```

Construct the members with the ordinary identifier-value machinery. Do not
coerce the key to a less precise `Str` value or the payload to `Any` merely to
make the rows homogeneous. The map's structural presentation may be broad,
but each row retains its exact key and payload.

`Just` and `nothing` are the existing core optional representation. Lookup
must construct them internally and must not depend on whether the source has
imported the `Std.Maybe`, `Std.Just`, or `Std.nothing` bindings.

### Concrete strings and total templates

For a concrete string:

```datra
~"abc"
```

return a singleton outer map containing the row for `"abc"`. A miss does not
remove the row; it changes only that row's value:

```datra
((key : "abc"; value : nothing))
```

`~a` evaluates `a`. If `a` evaluates to `"abc"`, it has the same result as
`~"abc"`; it never treats the spelling `a` as the lookup key.

A syntactic string template whose interpolations all evaluate to total values
is also a concrete string. It returns one row and does not require a foliage
capability:

```datra
~"arg%(2 + 2)"
```

returns the singleton row for `"arg4"`.

### Non-total templates

A template with at least one non-total capture describes a family of keys. For
example, `"arg%Nat"` describes `"arg0"`, `"arg1"`, and so on. `~` builds a map
containing one row for every member of the capture family.

The operator does not enumerate the map eagerly. Finite families expose their
finite row count; infinite families expose a lazy map of order type `omega`.
Accessing natural result position `n` constructs only foliage rank `n` and its
lookup row.

The scope consulted by every lazy row is the lexical scope captured when the
`~` expression is evaluated. Later access does not switch lookup to the
caller's scope.

## Capture compilation

### Retained template plan

A string-template value must retain both its ordinary string federation and a
capture plan:

```haskell
data EvaluatedStringTemplate = EvaluatedStringTemplate
  { stringTemplateSegments :: [EvaluatedStringTemplateSegment]
  , stringTemplateCaptureSchema :: InterpretedValue
  }

data EvaluatedStringTemplateSegment
  = EvaluatedStringLiteral String
  | EvaluatedStringCapture CaptureIndex InterpretedValue
```

The exact fields are provisional. The representation must retain:

- literal text and capture order;
- each capture's function-domain schema;
- the underlying bound used to enumerate that capture;
- the existing converted string federation used by specification and
  projection; and
- enough provenance to survive aliases and wrappers that preserve a
  `TemplateForm`.

`interpretStringTemplateWith` already evaluates interpolation expressions
before calling `toStringValue`. It should build this plan at that boundary.
Total interpolations are folded into adjacent literal text. Only non-total
interpolations become capture slots.

For a capture such as `%(_x : Nat)`, `_x` is slot metadata and `Nat` is the
enumerated bound. Domain preparation still sees the named slot, but generated
key text comes from the prepared payload. This distinction is what makes the
key `"arg4"` rather than `"arg(_x := 4)"`.

### The `^`-generic map-access rule

Capture admissibility is defined by an equivalence:

> A lookup capture plan is admissible if and only if the equivalent leading
> `^`-generic telescope can expose its ordinary map-access view.

Compilation should share `genericFunctionMapView` and
`ordinalIndexedValueFamily`, or extract their common family builder. It must not
reimplement the predicate in the lookup code.

The existing rule admits:

- an atomic value with an `orderedAtlasMapView` whose order type is at most
  `omega`; and
- a sequential product of admitted values, using the existing lexicographic
  product construction.

It therefore preserves the same coordinate order, dependency preparation, and
ordinal multiplication already observed through map access on generic
functions. Finite products may have transfinite order below
`omega ^ omega`, and foliage traversal can fairly reindex those positions.

The same rule rejects values without that semantic capability. Examples
include:

- `Any`;
- arbitrary functions or unions which do not expose an ordered family;
- coalized limit-endpoint ranges such as `from 0 to Infinity`; and
- wrappers which erase the ordered-map capability.

Ordinary generic functions remain callable when their `^` bound lacks a map
view; they simply do not expose that projection. A lookup template has no
callable fallback, so the same failure is a compilation error:

```datra
~"value%Any"    # compilation error
```

Add a diagnostic such as:

```haskell
ValueLookupCaptureHasNoGenericMapView CaptureIndex String
```

The diagnostic should identify the interpolation and render its evaluated
bound. Report it while compiling the `ValueLookup`, before constructing any
result row. It must not appear later as `nothing`, an empty map, or a failed map
access.

This check applies only when captures remain after total interpolation folding.
A total template always produces its one concrete row.

### Preparing capture tuples

The generic map view supplies one witness tuple at each source-family ordinal.
Before rendering a key, pass that tuple through the same argument-schema
preparation used by an ordinary function domain. In the current implementation
this means sharing the logic behind `argumentSchemaFromValue`,
`argumentSchemaValuesComplete`, and `overloadArgumentSchemaComplete` rather
than checking each witness with `of`.

Preparation provides the canonical payload for every slot, applies named and
positional rules consistently, and prevents template generation from drifting
away from function-call semantics.

Each prepared payload must have one canonical concrete string conversion.
Failure is a compilation error in the capture plan, not a skipped foliage row.

## Foliage ordering

Let the compiled capture family have ordinal order type `alpha` and ordinal
accessor `captureAt`. Construct:

```haskell
traversal = foliageMap alpha
```

The row at natural result rank `n` is defined by:

```text
source position = foliageMapPositionAt traversal n
capture tuple   = captureAt source position
prepared tuple  = ordinary function-domain preparation of capture tuple
key             = template rendered from prepared capture payloads
row             = (key : key; value : optional scope lookup at key)
```

`FoliageMap` is a bijection between natural ranks in the result and positions
below the supported source ordinal. Every capture tuple therefore appears
exactly once even when the source order is transfinite.

The result order type is:

- the finite natural `n` when `alpha` is finite `n`;
- `omega` when `alpha` is infinite; or
- `1` for a concrete string or total template, which has no capture family.

The output's ordinal order is deliberately not `alpha`: it is the natural
foliage traversal order. This is what allows ordinary result positions
`0, 1, 2, ...` to fairly observe every lane of a family such as
`omega + omega` or `omega ^ 2`.

The existing injectivity checks for string interpolation remain mandatory. If
two distinct prepared capture tuples render the same key, template compilation
fails with `NonInjectiveStringInterpolation` or a more specific equivalent;
the lookup map must not silently merge or duplicate a key.

## Scope lookup

Split name discovery from binding evaluation so absence can be represented
without catching unrelated errors:

```haskell
resolveOptionalScopeValue
  :: ReductionContext
  -> Scope
  -> [String]
  -> String
  -> Either InterpretingError (Maybe InterpretedValue)
```

The helper shares ordinary identifier resolution order, canonical aliases,
privacy rules, shadowing behavior, cycle detection, and scope protection with
`resolveIdentifierAccess`.

It returns `Right Nothing` only when no binding exists for the query. Once a
binding has been found, any error while evaluating it remains `Left error`.
The row's `key` field always retains the generated query string, even when an
internal canonical alias is used to resolve it.

## Lazy-map error propagation

The current `makeLazyMapValue` accessor has type:

```haskell
Ordinal -> Maybe InterpretedValue
```

That type cannot distinguish an unavailable ordinal from an error evaluating a
present binding. Converting a `Left` to `Nothing` would incorrectly turn a
broken binding into either a missing row or a missing value.

Extend the lazy-map/access boundary with a checked accessor, for example:

```haskell
data CheckedOrdinalValues value = CheckedOrdinalValues
  { checkedOrderType :: Ordinal
  , checkedValueAt
      :: Ordinal -> Either InterpretingError (Maybe value)
  }
```

and a corresponding checked lazy-map constructor. `accessValues` must propagate
the `Left` when the selected row is demanded. Finite and range access must
preserve the same behavior for every demanded member.

The ordinary pure `OrdinalOrderedValues` capability remains appropriate for
the capture family itself. Only the output row accessor needs the checked form,
because scope lookup can evaluate deferred bindings. Do not globally weaken
pure ordered-map laws to accommodate this operator.

## Canonical reverse matching

String-template matching needs a dedicated operation shared by string
specification, `of` checks, template-selection projections, and lookup-template
validation:

```haskell
matchCanonicalTemplate
  :: CanonicalStringCodec
  -> EvaluatedStringTemplate
  -> String
  -> Decision PreparedTemplateCaptures
```

Keep the existing finite split search over literal delimiters, but replace the
leaf call to general federation membership. For each possible split:

1. Decode captured substrings with `decodeCanonicalString`.
2. Require every candidate to re-render to exactly the same substring.
3. Submit the candidate tuple to ordinary function-domain preparation.
4. Extract the prepared capture payloads.
5. Reconstruct the complete string from those payloads.
6. Accept only if reconstruction equals the input byte for byte.

Distinct splits which prepare to the same tuple are one match. Distinct
prepared tuples retain the existing ambiguity error.

The reconstruction check excludes identifier-assignment syntax from generated
or matched keys:

```datra
"arg4" of "arg%(_x : Nat)"             # true
"arg(_x := 4)" of "arg%(_x : Nat)"     # false
```

The successful witness retains the prepared tuple so
`Evaluation.Specification.Projection` continues to expose the whole string at
position zero and captures at subsequent positions.

This rule is specific to canonical string templates. Declarative `%` syntax
patterns continue to match source AST structure.

## Syntax and AST

### Parsing

Add a real expression constructor:

```haskell
ValueLookup Expression
```

and the corresponding `OperatorExpression` constructor. `~` remains a tight
prefix operator:

```text
~a                 == ValueLookup (IdentifierReference "a")
~"a"               == ValueLookup (AsciiStringLiteral "a")
~"arg%Nat"         == ValueLookup <template>
~(a + b)           == ValueLookup (Addition a b)
```

Postfix access applies to the result map, so `~"arg%Nat"[0]` selects the first
lookup row. Parentheses are required when the key expression contains a looser
infix or map operator.

Remove `namedAccessNames` and `expandedNamedAccess` from the `~` parser path.
`~(a, b)` is one lookup expression, not two strict name lookups. The lone token
`~` remains a parse error, and existing token guards continue to distinguish
`~`, `~>`, and `<~`.

### Rendering and traversal

Update normalization, child traversal, source rendering, canonical AST
rendering, syntax rewriting, closure analysis, and serialized-AST parsing for
the new node.

Source rendering prints `~` followed by its operand at prefix precedence. It
must round-trip to `ValueLookup`; it must not infer `~` from a `ScopeAccess`
shape.

### Strict generated references

Compiler-generated closure and canonical-dependency references remain strict.
Represent them as `IdentifierReference` or explicit `ScopeAccess` nodes, and
render explicit current-scope access when a quoted name is required:

```datra
this."value with spaces"
```

Remove the `scopeNames` renderer shortcut. Generated code must never use
`ValueLookup`, because doing so would change a strict dependency into a map of
optional values.

## Interpreter structure

A suggested top-level decomposition is:

```haskell
evaluateValueLookup
  :: ReductionContext
  -> Scope
  -> [String]
  -> InterpretedValue
  -> Either InterpretingError InterpretedValue

compileLookupCaptureFamily
  :: EvaluatedStringTemplate
  -> Either InterpretingError OrdinalIndexedFamily

lookupRowAt
  :: Scope
  -> FoliageMap
  -> Natural
  -> Either InterpretingError (Maybe InterpretedValue)
```

`evaluateValueLookup` distinguishes:

1. a total concrete string, producing a checked singleton map; and
2. a retained non-total template plan, compiling its `^`-generic map view and
   producing a checked foliage-indexed map.

Any other operand produces `ValueLookupRequiresString`.

`compileLookupCaptureFamily` should be a thin adapter over the generic map-view
machinery. The implementation should make it difficult for a future change to
generic projection rules to update one feature but not the other.

## Diagnostics

Add or reuse diagnostics for:

- `ValueLookupRequiresString` when the operand is neither a concrete string nor
  a retained string template;
- `ValueLookupCaptureHasNoGenericMapView` when a non-total capture fails the
  same map-view rule as a `^` generic bound;
- `ValueLookupCaptureNotCanonical` when a generated capture does not have one
  canonical concrete string conversion; and
- the existing `NonInjectiveStringInterpolation` and
  `AmbiguousStringTemplate` cases.

The capture-family diagnostics are compilation errors for the whole lookup.
They are never encoded as rows. A missing scope binding is not a diagnostic; it
is a row whose `value` is `nothing`.

## Compatibility

This change is intentionally source- and result-incompatible with old `~`:

| Source | Old meaning | New meaning | Strict replacement |
| --- | --- | --- | --- |
| `~a` | value at literal name `a` | singleton or foliage map for the string value of `a` | `a` |
| `~"a"` | value at name `a` | singleton row for key `a` | `a`, or `this."a"` when quoting is required |
| `~(a, b)` | concatenation of two strict lookups | one lookup over the evaluated expression `(a, b)` | `(a, b)` |
| `~"arg%Nat" 4` | lookup-produced function application in the earlier proposal | no longer supported | select the `"arg4"` row from `~"arg%Nat"` |

Canonical rendering, retained begin-block rendering, and serialized closures
must be migrated in the same change so generated strict references never
acquire the new map semantics.

## Test plan

### Parser and rendering regressions

Update `DatraParsingTests` to cover:

- `~a`, `~"a"`, `~"arg%Nat"`, and `~(a + b)` as `ValueLookup` nodes;
- postfix selection from a lookup result;
- rejection of a lone `~`;
- `~(a, b)` no longer expanding into two scope accesses;
- source and canonical AST round trips; and
- explicit rendering of generated strict references as `this.name` or
  `this."quoted name"`.

### Concrete and total-template regressions

Add cases proving that:

- a literal key produces a singleton outer map;
- a hit retains the key and stores `Just payload` in `value`;
- a miss retains the key and stores `nothing` in `value`;
- `~a` uses the string value of `a`;
- a private quoted key follows ordinary lexical resolution rules;
- aliases and shadowing agree with strict identifier resolution;
- `~"arg%(2 + 2)"` produces exactly one row for `"arg4"`; and
- an existing binding failure propagates when its row is demanded.

### Foliage traversal regressions

Add cases for:

- the first several rows of `~"arg%Nat"`;
- a finite valued range producing exactly its finite number of rows;
- a two-capture finite product using the same coordinate order as `^` generic
  map access;
- `Nat; Nat`, `omega + omega`, and another transfinite product demonstrating
  the existing `FoliageMap` interleaving;
- every tested source-family position round-tripping through
  `foliageMapRankOf` to the corresponding result row;
- missing bindings remaining as rows rather than being filtered out;
- map and range access over the lazy result; and
- lexical scope capture for rows demanded after the producing block exits.

### Capture admissibility regressions

Use the existing generic-family projection matrix as the oracle. Add paired
tests showing that each bound accepted for `^` map access is accepted as a
lookup capture and each unsupported bound is rejected during lookup
compilation.

At minimum cover:

- finite and infinite valued ranges;
- named ordered Atlas maps;
- sequential products;
- `Any` rejection;
- limit-endpoint range rejection; and
- a wrapper which does and one which does not preserve the ordered-map view.

### Canonical string regressions

Add direct membership, specification, projection, and lookup-generation cases
proving that:

- `"arg4"` matches and is generated by `"arg%(_x : Nat)"`;
- `"arg(_x := 4)"` neither matches nor appears as a generated key;
- noncanonical spellings such as padded naturals do not match;
- projections return the prepared capture payload;
- multiple holes use ordinary function-domain ordering and naming rules;
- ambiguous splits are rejected; and
- declarative `%` syntax matching remains unchanged.

### Cross-feature regressions

Update `FunctionClosureTests`, retained-block rendering tests, CLI golden
fixtures, and source snapshots containing old `~` sugar. Add a closure
round-trip proving that a strict generated dependency is not converted into a
lookup map.

## Implementation sequence

1. Add the `ValueLookup` AST constructors and update traversal, parsing,
   rendering, and strict generated-reference rendering.
2. Retain evaluated string-template capture plans and fold total
   interpolations to concrete strings.
3. Extract or reuse the exact `^`-generic map-view builder as the capture-family
   admissibility boundary.
4. Refactor scope resolution into absent-aware discovery and checked binding
   evaluation.
5. Add checked lazy-map access so row construction can propagate deferred
   binding failures.
6. Implement singleton lookup maps and foliage-reindexed template lookup maps.
7. Replace string-template leaf membership with canonical function-domain
   preparation while retaining projection witnesses.
8. Update existing regressions and add the parser, foliage, admissibility,
   canonical matching, closure, and golden tests above.

## Acceptance criteria

The change is complete when all of the following hold:

1. `~a` evaluates `a` as a string expression and never treats its spelling as
   the key.
2. Every result is a map of `(key; value)` rows, including concrete strings and
   total templates.
3. Every admissible template key has exactly one row, including absent keys.
4. Each row stores `Just resolvedValue` or `nothing` in its `value` member.
5. Non-total template rows follow `FoliageMap` traversal order.
6. Capture admissibility is exactly the map-access rule for `^` generics;
   `Any` is rejected during lookup compilation.
7. Total templates bypass capture enumeration and produce one concrete row.
8. `"arg%(_x : Nat)"` generates and matches `"arg4"`, never
   `"arg(_x := 4)"`.
9. Lazy row access propagates failures from present bindings instead of
   changing them to `nothing`.
10. Compiler-generated strict references round-trip without using `~`.
